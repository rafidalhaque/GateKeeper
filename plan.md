## 16. Super Admin, Roles & Permission System (Feature 10)

### 16.1 Roles Overview

The system supports **role-based access control (RBAC)** with:

- **Super Admin**
  - Full, unrestricted access
  - Can manage:
    - Events
    - Roles
    - Permissions
    - Admins / Booth Managers
    - System-level configuration
- **Custom Roles**
  - Created by Super Admin
  - Assigned to admin users
  - Permissions are granular and explicit

---

### 16.2 Permission Model

Permissions are **task-based**, auto-generated, and system-reserved.

Each permission represents **one atomic action**, for example:
- `participant.read`
- `participant.create`
- `participant.update`
- `participant.delete`
- `team.read`
- `team.create`
- `attendance.mark`
- `ticket.send`
- `email.send_bulk`
- `csv.import`
- `event.configure`
- `role.manage`
- `permission.view`

#### Key Rules
- Permissions are:
  - **Auto-generated by the system**
  - **Non-deletable**
  - **Non-editable**
- Only **roles** reference permissions
- Prevents permission drift and accidental privilege escalation

---

### 16.3 Permission Chunks (Feature-Based Grouping)

For UI and clarity, permissions are grouped into **feature chunks**, such as:

#### Participants
- `participant.read`
- `participant.create`
- `participant.update`
- `participant.delete`

#### Teams
- `team.read`
- `team.create`
- `team.update`
- `team.delete`

#### Attendance
- `attendance.read`
- `attendance.mark`

#### Tickets
- `ticket.read`
- `ticket.generate`
- `ticket.send`

#### Emails
- `email.read_logs`
- `email.send_bulk`

#### CSV Import
- `csv.import`

#### Events
- `event.read`
- `event.create`
- `event.update`
- `event.delete`
- `event.configure`

#### Roles & Security
- `role.read`
- `role.create`
- `role.update`
- `role.delete`
- `permission.read`

---

### 16.4 Database Schema (RBAC)

#### roles
- id (integer, pk)
- name (string, unique)
- description
- created_at
- updated_at

#### permissions
- id (integer, pk)
- key (string, unique)  
  (example: `participant.read`)
- description
- feature_group (string)
- system_reserved (boolean = true)

#### role_permissions
- role_id (fk → roles.id)
- permission_id (fk → permissions.id)
- composite primary key (role_id, permission_id)

#### admin_users
- id (uuid, pk)
- supabase_user_id (string, unique)
- role_id (fk → roles.id)
- created_at
- updated_at

---

### 16.5 Super Admin Capabilities

Super Admin can:
- Create, edit, delete **roles**
- Assign **multiple permissions** to a role (multi-select UI)
- Assign roles to admin users
- View all system permissions (read-only)
- Override event-level restrictions if needed

Super Admin is **not permission-limited** and bypasses checks.

---

### 16.6 Admin Panel – Permission Management UI

#### Permissions Page
- Read-only list of:
  - Permission key
  - Description
  - Feature group
- No edit/delete options

#### Role Management Page
- Create new role
- Multi-select permissions (grouped by feature)
- Edit role permissions
- Delete role (if not in use)

#### Admin Assignment
- Assign role to admin / booth manager
- Changes apply immediately

---

### 16.7 Backend Enforcement (Flask)

- Each protected endpoint declares required permission(s)
- Middleware checks:
  - Supabase JWT validity
  - User role
  - Role → permission mapping
- If missing permission → HTTP 403

Example:
- `/api/participants` (POST) → requires `participant.create`
- `/api/checkin/confirm` → requires `attendance.mark`

---

### 16.8 Why This Design

- Prevents overpowered booth managers
- Scales cleanly as features grow
- Permissions stay consistent across events
- Matches enterprise-grade RBAC patterns
- Easy to audit and reason about

---

### 16.9 Default Roles (Seeded)

- **Super Admin**
  - All permissions (implicit)
- **Event Admin**
  - Full event + participant + ticket access
- **Booth Manager**
  - `participant.read`
  - `attendance.read`
  - `attendance.mark`
